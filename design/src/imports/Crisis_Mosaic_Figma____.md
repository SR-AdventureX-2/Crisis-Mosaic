## Part A:需求整理

### 1. 项目基础信息

#### 项目名称

Crisis Mosaic(直接使用英文名)

#### 一句话说明

> 一张知道自己缺什么的灾害地图:通过 Missing Piece Engine 主动找出最可能改变救援决策的未知信息,并向最合适的人定向求证——一块小碎片进入系统,整套救援方案瞬间重排。

#### 目标用户

**产品语境**(界面为谁设计):

- 用户类型 1:灾区居民——极简匿名上报,回答系统的定向问题
- 用户类型 2:现场志愿者——接收信息确认任务(本次并入居民端,不做独立端)
- 用户类型 3:救援指挥人员——查看碎片地图、盲区、当前方案

**交付语境**(Demo 给谁看):黑客松评委。所有页面为 3 分钟五幕演示服务。

#### 核心痛点

- 痛点 1:信息分散在居民、医院、志愿者、司机手中,每人只有一块碎片,没有人看得见全貌
- 痛点 2:信息冲突被普通系统"保留最新一条"静默覆盖,指挥端看到报告数量却不知道**缺什么**
- 痛点 3:关键位置信息空白(盲区),而最弱势的人往往没有能力持续发声

#### 产品目标

- 目标 1:让评委相信**这个机制真的有用**——主动发现信息缺口比收集更多报告更有价值
- 目标 2:五幕演示证明三个核心能力:**碎片能组合 / 冲突不被覆盖(系统有自己的判断) / 系统主动找到最重要的未知**
- 目标 3:交付可双机实时演示的 Android APP

#### 产品关键词

- 万花筒 / 马赛克(kaleidoscope 视觉母题)
- 信息碎片(带完整上下文的 Fragment,不是地图 Marker)
- 盲区黑洞(我们知道什么,以及我们还不知道什么)
- 主动求证(定向问题,不是广撒网)
- 教堂彩窗(浅底 + 玻璃碎片 + 铅条描边,美术馆装置感)
- 诚实的不确定性(展示冲突,不假装知道真相)

### 4. 核心用户流程

#### 流程 1:五幕两拍演示主流程(指挥端,手机 1)

##### 流程目标

评委在 3 分钟内看懂:一块很小的信息进入系统,整套救援路径瞬间重新排列。

##### 触发条件

打开 APP,Splash 播完自动进入幕 1 画面拍;讲解人以下滑手势控制全部节奏,不依赖动画计时。

##### 主路径(杭州 · 台风过境 · 运河片区内涝)

1. Splash:完整万花筒(约 2s)→ 破碎(约 1s)→ 转场入杭州拱墅 · 运河片区地图。
2. **拍 1A**:预设碎片陆续飞入落位——A 社区(运河西岸,60 人被困)、B 仓库(200 箱饮用水)、C 医院(剩 12 床位)……其中**沿江路出现冲突碎片对**:「14:00 车辆可通行(居民)」与「14:28 路面已被淹(司机)」两块长条碎片错位重叠、交替闪烁。
3. 下滑 → **拍 1B**:信息卡升起:「已收到碎片 27 条 · 检测到 1 组冲突(沿江路)· 方案计算中…」,小字:「两条观察不一致,系统已保留双方并推断:水位上涨中」。
4. 下滑 → **拍 2A**:画面整体压暗,大关桥位置的黑洞放大凸显。
5. 下滑 → **拍 2B**:「⚠ 最大信息盲区:大关桥通行状态 — 影响 3 条配送路线、约 60 人」。
6. 下滑 → **拍 3A**:黑洞处出现**透明碎片占位**,呼吸闪烁。
7. 下滑 → **拍 3B**:「已向桥梁附近 1 位居民发出确认请求 · 等待回应…」。此时切手机 2 演示居民端提交;提交成功后,实色长条碎片从屏幕边缘弧线飞入填进占位,卡片更新「碎片已返回:车辆无法通行,行人可通行」。
8. 下滑 → **拍 4A**:全屏重排动画——原路线(B 仓库→卡车→大关桥→A 社区)拆解散开,重组为「卡车至桥西 → 志愿者步行过桥 → 社区推车接力 → A 社区」。
9. 下滑 → **拍 4B**:新方案文字逐行更新,置信度 42% → 78%。
10. 下滑 → **幕 5 镜片舞台**:5 个镜片图标全部解锁,依次点击 Logistics / Medical / Vulnerability / Information,碎片随镜片重排;Information Lens 指出下一个关键未知:「C 医院备用电量,20 分钟后成为关键」。
11. 下滑 → **金句卡**:One small piece can turn the whole kaleidoscope.(中文小字:一块小碎片,足以转动整个万花筒。)

##### 分支路径

- 上滑任意时刻回退一拍,可回溯、可重放(评委要求重看重排:上滑两拍回 3B 再下滑)。
- 幕 5 内点击镜片不消耗拍;下滑才离开幕 5。
- 点击任意碎片 → 详情弹层(P1);弹层打开时暂停拍手势。

##### 异常路径

| 异常情况 | 页面表现 | 用户可操作 | 后续结果 |
|---|---|---|---|
| 手机 2 提交延迟 | 拍 3B 等待态可无限停留,占位呼吸闪烁 | 讲解人话术垫场 | 碎片到达后继续 |
| 现场网络中断 | 碎片不飞入 | **长按黑洞 3 秒注入大关桥碎片**(观众不可见) | 演示无缝继续 |
| 误滑 | 跳到错误的拍 | 上滑 / 下滑回到正确的拍 | 无损恢复 |

##### 冲突展示说明(拍 1A/1B 内嵌,不占独立幕)

- **数据**:两条 road_status 碎片互相 conflicts_with——「沿江路 14:00 车辆可通行,observer=居民」vs「沿江路 14:28 路面已被淹,observer=司机」。
- **视觉**:两块钴蓝长条碎片错位重叠约 8px,交替置顶 + 透明度交替闪烁(1.2s 循环)——一眼看出"这里有两个说法"。
- **系统判断**(可解释规则引擎,不依赖大模型;答辩时是加分项):不覆盖、不静默二选一,而是按 observed_at 推断时间线——「14:00 前可通行 → 14:28 后可能被淹 → 状态变化中 · 置信度中等 · 建议改道或再次确认」。
- **讲稿钩子**:"注意沿江路——两条信息在打架。系统不会用新信息覆盖旧信息,也不盲听任何一方,它保留冲突、推断变化,**有自己的判断**。"
- **P1 详情弹层**:点击冲突对展开完整时间线(两条观察 + 推断结论 + 建议)。

##### 对应 Figma Frames

见第 7 节命名清单。

#### 流程 2:居民上报闭环(居民端,手机 2)

##### 流程目标

居民 30 秒内、极少文字、无注册,完成一次改变全局的信息提交。

##### 主路径

1. 居民端首页:6 按钮(救援 / 医疗 / 饮水 / 食物 / 避难 / 上报道路)+ 顶部定向任务卡「附近有一个关键确认请求」(呼吸光效)。
2. 点任务卡(或「上报道路」)→ 定向问题页:「你现在能看见大关桥吗?」。
3. 4 选 1:车辆可通行 / 仅行人可通行 / 完全中断 / 无法判断。未选中时提交按钮禁用。
4. 点提交 → Sending(按钮 loading,防重复提交)。
5. 提交成功页:「已收到你的碎片 · **你的信息正在影响 3 条救援路线**」+ 小碎片入位动画 + [返回首页]。
6. 同时手机 1 拍 3B 碎片飞入。

##### 分支路径

- 无定向任务时,居民可从 6 按钮主动上报;Demo 只完整实现「上报道路」路径,其余 5 个按钮进入同构简化页。

##### 异常路径

| 异常情况 | 页面表现 | 用户可操作 | 后续结果 |
|---|---|---|---|
| 未选择就点提交 | 按钮保持禁用态 | 先选择 | — |
| 网络失败 | 「已离线暂存,网络恢复后自动同步」(P1) | 返回首页 | 恢复后自动发送 |
| 重复点击 | Sending 态锁定按钮 | 等待 | 只提交一次 |

##### 对应 Figma Frames

- Resident / Home / Default(含任务卡)
- Resident / Task / BridgeQuestion(Default / Selected / Sending)
- Resident / Submit / Success
- Resident / Submit / Offline(P1)

#### 流程 3:镜片切换(幕 5)

##### 镜片体系(5 个,Rescue 为默认)

| 镜片 | 何时出场 | 碎片排列重点 | 信息卡内容 |
|---|---|---|---|
| Rescue 救援(默认) | 幕 1~4 全程 + 幕 5 起点 | 被困人数、可达路线、救援位置 | 即五幕主线内容 |

##### 交互规则

- 幕 1~4:左缘 5 图标可见,Rescue 高亮为当前镜片,其余 4 个 disabled(轻透明度)——评委能预感"后面有戏"。
- 幕 5:全部解锁;点击切换,重排动画 600ms;切换不消耗拍。

#### 流程 4(P1):碎片详情弹层

##### 流程目标

证明"每块碎片都有完整上下文,不是地图 Marker"——评委自由把玩时的深度感来源。

##### 主路径

1. 任意拍中点击一块碎片 → 底部弹层升起(约 55% 屏高)。
2. 弹层内容:类型图标 + 地点 | 观察时间 / 提交时间(分开展示)| 观察者角色(匿名)| 置信度条 | 时效倒计时(临期变琥珀色)| 证据缩略图(如有)。
3. 冲突碎片额外显示**时间线区块**:两条观察按时间排列 + 系统推断结论 + 建议。
4. 关闭:✕ 按钮或点遮罩(**不用下滑关闭**,避免与推进拍手势冲突;弹层打开期间拍手势暂停)。

### 5. 数据与内容规则

#### 数据字段:Fragment(信息碎片)

| 字段 | 类型 | 是否必填 | 示例 | 规则 | 空值表现 |
|---|---|---|---|---|---|
| type | Enum | 是 | road_status | 人员需求 / 物资 / 道路 / 医疗 / 避难 | — |
| location | GeoPoint + String | 是 | 大关桥 | 坐标 + 地名 | 无法定位时仅存地名 |
| value | String/Enum | 是 | 车辆无法通行 | 定向问题时为枚举 | — |
| observer | Enum | 是 | 附近居民 | 居民/志愿者/救援队,匿名不存身份 | 显示"匿名" |
| observed_at | Time | 是 | 14:32 | 观察时间≠提交时间,分开记录 | 用提交时间替代并标注 |
| submitted_at | Time | 是 | 14:35 | 系统自动记录 | — |
| confidence | Number | 是 | 0.7 | 0~1,由来源距离/证据/是否亲见计算 | 默认 0.5 |
| visibility | Enum | 是 | rescue_only | public / rescue_only | 默认 public |
| expires_after | Duration | 是 | 30 minutes | 按类型给默认时效,道路类最短 | — |
| evidence | List | 否 | ["photo"] | 照片可选,不强制 | 无证据则 confidence 降档 |
| supports | List<id> | 否 | [] | 与哪些碎片互相支持 | — |
| conflicts_with | List<id> | 否 | ["fragment_102"] | 冲突不覆盖,并列展示 + 时间线推断 | — |

#### 信息优先级公式(Missing Piece Engine,可解释算法,不依赖大模型)

```text
Priority = PopulationImpact × DecisionSensitivity × Uncertainty × FreshnessDecay × Observability ÷ AcquisitionCost
```

#### 文案规则(中文为主 + 英文金句)

| 文案类型 | 示例 | 规则 |
|---|---|---|
| 盲区提示 | ⚠ 最大信息盲区:大关桥通行状态 — 影响 3 条配送路线、约 60 人 | 必须说明影响什么决策、多少人 |
| 定向问题 | 你现在能看见大关桥吗? | 一次只问一个问题,选项≤4 |
| 提交成功 | 你的信息正在影响 3 条救援路线 | 数字来自接口返回,给参与感 |
| Loading | 方案计算中… | 短,配碎片飞入动画 |
| **冲突展示** | 沿江路 · 2 条观察不一致:14:00 车辆可通行(居民)/ 14:28 路面已被淹(司机)· 推断:水位上涨中 · 建议改道或再次确认 | 不判真假、不覆盖;展示时间线 + 系统推断 + 建议 |
| 过期提醒 | 该信息已超过 30 分钟,需要重新确认 | 配裂纹视觉 |
| 数据水印 | 模拟演练数据 · 杭州 | 常驻角落小字,避免真实地名引发误解 |
| 结尾金句 | **One small piece can turn the whole kaleidoscope.**<br>一块小碎片,足以转动整个万花筒。 | 英文大字 + 中文小字 |
