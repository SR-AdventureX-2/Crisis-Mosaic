# Crisis Mosaic 极简需求文档 v2.0

> 来源: `/Users/songxiaojing/Desktop/Crisis Mosaic Figma交付文档.md`  
> 更新日期: 2026-07-23  
> 产品原则: 最少页面、最少操作、信息即时可见、信息即时可改

## 1. 产品概述

### 1.1 产品定位

Crisis Mosaic 是一个用于灾害现场快速交换信息的极简工具。

产品只解决三个核心问题:

1. 受灾人员可以立即输入并提交现场信息。
2. 救援人员可以立即看到最新信息。
3. 信息发生变化时,提交者可以立即修改,救援端同步更新。

### 1.2 核心价值

缩短“现场情况发生变化”到“救援人员看到变化”之间的时间,减少任何不必要的页面、选择和确认操作。

### 1.3 目标用户

| 用户 | 核心任务 |
|---|---|
| 受灾人员 | 快速上报自己看到的情况,并在情况变化后修改信息 |
| 救援人员 | 快速浏览最新现场信息,识别地点、时间和紧急程度 |

## 2. 产品目标

### 2.1 核心目标

- 受灾人员从打开上报页面到成功提交不超过 20 秒。
- 完成一次上报最多需要 2 次核心操作:输入信息、点击提交。
- 救援人员打开页面后无需额外操作即可看到最新信息。
- 信息提交或修改后,救援端应在 2 秒内更新。
- 用户不需要注册、登录或学习复杂操作。

### 2.2 非目标

本版本明确不做以下内容:

- 不做五幕式或分镜式演示。
- 不做上下滑动推进剧情。
- 不做万花筒开场、碎裂动画和结尾金句页。
- 不做镜片切换、复杂地图图层和信息碎片重排。
- 不做复杂的信息盲区、冲突推理和置信度演出。
- 不做救援路线自动重排动画。
- 不做多级分类、多步问卷和复杂表单。
- 不做注册、登录、账号资料和社交功能。
- 不做非必要动效、装饰性卡片和解释性页面。

## 3. 产品范围

### 3.1 P0 必须实现

| 模块 | 功能 |
|---|---|
| 角色入口 | 进入 App 后选择“我要上报”或“查看信息” |
| 受灾人员上报 | 在单页输入现场信息并提交 |
| 自动补充信息 | 自动记录上报时间;获得授权后自动记录位置 |
| 上报成功反馈 | 页面内显示简短成功状态,不跳转到新页面 |
| 修改信息 | 提交者可在原页面修改最近一次上报并重新提交 |
| 救援信息列表 | 按更新时间倒序实时展示全部现场信息 |
| 信息更新 | 修改后的内容立即替换旧内容,并标记“已更新” |
| 实时同步 | 新增和修改信息实时推送到救援端 |
| 基础状态 | 提交中、提交成功、提交失败、无信息、连接中断 |

### 3.2 P1 可后续实现

| 模块 | 功能 |
|---|---|
| 紧急标记 | 受灾人员可勾选“情况紧急” |
| 救援处理状态 | 救援人员可将信息标记为“已查看”或“已处理” |
| 简单筛选 | 仅保留“全部 / 紧急”两个选项 |
| 离线暂存 | 无网络时保存在本机,恢复连接后自动提交 |

## 4. 信息架构

产品只保留三个页面:

1. 角色选择页。
2. 受灾人员上报页。
3. 救援人员信息页。

不设置底部导航,不设置多层详情页。用户可以通过页面左上角返回角色选择页。

## 5. 核心用户流程

### 5.1 受灾人员首次上报

1. 用户打开 App。
2. 点击“我要上报”。
3. 在输入框直接描述现场情况。
4. 点击“提交信息”。
5. 当前页面显示“已提交”,输入内容保持可见并可继续修改。

核心操作数:2 次。

### 5.2 受灾人员修改信息

1. 用户回到上报页,看到最近一次提交内容。
2. 直接修改文字。
3. 点击“更新信息”。
4. 救援端实时显示新内容和“已更新”标记。

核心操作数:2 次。

### 5.3 救援人员查看信息

1. 用户打开 App。
2. 点击“查看信息”。
3. 页面自动显示最新现场信息,最新更新排在最前。

核心操作数:1 次。进入页面后无需点击信息卡即可阅读完整核心内容。

## 6. 页面需求

### 6.1 角色选择页

页面只展示产品名称和两个主要按钮:

- 我要上报
- 查看信息

要求:

- 两个按钮垂直排列,尺寸足够大,便于单手操作。
- 不展示产品介绍、功能说明、轮播图或装饰动画。
- 默认记住上一次选择;再次打开 App 时可直接进入对应页面。
- 页面保留“切换身份”入口,避免用户被锁定在单一角色。

### 6.2 受灾人员上报页

页面从上到下只保留以下内容:

| 区域 | 需求 |
|---|---|
| 标题 | “上报现场信息” |
| 位置信息 | 自动显示当前位置或简短地点;定位失败时允许手动输入地点 |
| 信息输入框 | 大尺寸多行输入框,占页面主要区域 |
| 提交按钮 | 首次为“提交信息”,提交后改为“更新信息” |
| 状态提示 | 在按钮附近显示提交中、已提交、提交失败或离线暂存状态 |

输入框要求:

- 提示文案:“请描述你看到的情况,例如积水、道路、受伤人员或所需物资”。
- 不要求用户先选择信息类型。
- 不要求填写姓名、电话或身份证明。
- 内容为空时提交按钮不可用。
- 提交后不清空内容,方便用户立即修改。
- 页面自动记录首次提交时间和最后更新时间。

### 6.3 救援人员信息页

页面从上到下只保留以下内容:

| 区域 | 需求 |
|---|---|
| 顶部栏 | 标题“现场信息”和连接状态 |
| 信息列表 | 按最后更新时间倒序排列 |
| 信息卡 | 直接展示地点、信息正文、时间和更新状态 |
| 空状态 | “暂时没有现场信息” |

每条信息卡必须直接显示:

- 地点。
- 完整信息正文,默认最多显示 6 行;超出时可展开。
- 首次上报时间或最后更新时间。
- “新信息”或“已更新”状态。
- P1 阶段的“紧急”标记。

救援人员无需点击进入详情页即可读取决定行动所需的核心信息。

## 7. 交互要求

### 7.1 保留的交互

| 交互 | 行为 |
|---|---|
| 点击角色按钮 | 进入对应页面 |
| 输入文字 | 编辑现场信息 |
| 点击提交 | 创建一条现场信息 |
| 点击更新 | 更新最近一次现场信息 |
| 下拉刷新 | 网络异常或用户需要主动确认时重新拉取列表 |
| 点击展开 | 仅当信息正文超过 6 行时展开全文 |

### 7.2 删除的交互

- 删除上下滑动推进或回退场景。
- 删除地图拖动、缩放和多图层切换。
- 删除长按触发隐藏功能。
- 删除碎片点击、弹层和复杂详情页。
- 删除多步骤选项问答。
- 删除动画驱动的路线重排。
- 删除需要用户理解的手势操作。

### 7.3 反馈规则

- 按钮点击后立即进入加载状态,防止重复提交。
- 提交成功后在当前页面显示“已提交”,不弹出模态框。
- 修改成功后显示“已更新”。
- 提交失败时保留全部输入内容,显示“提交失败,请重试”。
- 新信息到达救援端时插入列表顶部,使用不超过 300ms 的轻微淡入。
- 除页面切换和列表更新外,不使用其他动画。

## 8. 视觉设计要求

### 8.1 总体风格

设计必须简单、克制、清晰,以快速阅读和快速操作为第一优先级。

- 使用纯色背景,不使用渐变、纹理、光效或装饰图形。
- 全局只使用一种主色、一种强调色和中性色。
- 卡片圆角不超过 8dp,阴影尽量取消或保持极弱。
- 不使用玻璃拟态、3D、万花筒、碎片化造型或复杂插画。
- 不使用大面积品牌展示和情绪化文案。
- 每个页面只保留一个主要操作。
- 图标仅在比文字更直观时使用。
- 所有文字保持高对比度,正文不得使用过浅灰色。

### 8.2 建议色彩

| 用途 | 色彩建议 |
|---|---|
| 页面背景 | 白色或接近白色 |
| 主要文字 | 深灰或黑色 |
| 主操作 | 稳定、醒目的蓝色 |
| 紧急状态 | 红色,仅用于真正紧急的信息 |
| 成功状态 | 绿色,仅用于提交成功反馈 |

### 8.3 可用性

- 设计基准为 Android 竖屏 393×852dp。
- 主要按钮高度不小于 52dp。
- 所有可点击区域不小于 48×48dp。
- 输入框和主要按钮应处于单手容易触达的区域。
- 系统字体放大后,正文和按钮文字不得截断或重叠。
- 不依赖颜色单独表达状态,同时使用明确文字。

## 9. 数据需求

### 9.1 Report 数据结构

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | String | 是 | 信息唯一 ID |
| content | String | 是 | 用户输入的现场信息 |
| location_text | String | 是 | 自动定位结果或手动输入地点 |
| latitude | Number | 否 | 纬度 |
| longitude | Number | 否 | 经度 |
| created_at | Time | 是 | 首次提交时间 |
| updated_at | Time | 是 | 最后更新时间 |
| is_updated | Boolean | 是 | 是否被修改过 |
| is_urgent | Boolean | 否 | P1 紧急标记 |
| status | Enum | 否 | P1: new / viewed / resolved |
| local_owner_token | String | 是 | 本机修改最近一次信息所需的匿名凭证 |

### 9.2 数据规则

- 信息按 `updated_at` 倒序展示。
- 修改信息时更新原记录,不创建内容重复的新记录。
- 救援端只展示最新版本,避免新旧内容同时出现造成误判。
- 服务端保留修改记录用于审计,但本版本界面不展示历史版本。
- 不采集姓名、手机号等非必要个人信息。

## 10. 接口需求

| 接口 | 方法 | 路径 | 用途 |
|---|---|---|---|
| 获取信息列表 | GET | `/api/reports` | 救援端获取按更新时间排序的信息 |
| 创建信息 | POST | `/api/reports` | 受灾人员提交现场信息 |
| 更新信息 | PATCH | `/api/reports/:id` | 修改最近一次提交的信息 |
| 实时事件流 | WS | `/ws` | 推送 `report.created` 和 `report.updated` |

创建或更新成功后,接口应返回完整的最新 Report 数据。

## 11. 状态需求

| 状态 | 受灾人员端 | 救援人员端 |
|---|---|---|
| Loading | 按钮显示提交中,不可重复点击 | 首次加载显示简洁进度指示 |
| Success | 显示“已提交”或“已更新” | 新信息自动出现在列表顶部 |
| Empty | 输入框保持可编辑 | 显示“暂时没有现场信息” |
| Error | 保留输入内容并显示重试按钮 | 保留已有列表并显示连接异常 |
| Offline | P1:保存到本机并等待自动提交 | 展示最后一次成功获取的数据 |

## 13. 验收标准

| 编号 | 场景 | 验收标准 |
|---|---|---|
| AC-01 | 选择角色 | 用户可通过一个按钮进入上报页或信息页 |
| AC-02 | 首次上报 | 用户输入内容并点击一次提交后完成上报 |
| AC-03 | 输入保护 | 内容为空时不可提交;失败时输入内容不丢失 |
| AC-04 | 信息查看 | 救援人员进入页面后无需点击即可看到最新信息正文 |
| AC-05 | 实时新增 | 新信息提交后 2 秒内出现在救援列表顶部 |
| AC-06 | 即时修改 | 修改后 2 秒内替换救援端旧内容并显示“已更新” |
| AC-07 | 排序 | 信息始终按最后更新时间倒序排列 |
| AC-08 | 视觉简洁 | 页面无渐变、复杂插画、装饰动效和嵌套卡片 |
| AC-09 | 最少交互 | 首次上报不超过 2 次核心操作;查看信息不超过 1 次核心操作 |
| AC-10 | 异常恢复 | 网络失败后用户输入不丢失,可直接重试 |

## 14. 研发优先级

1. 完成角色选择页、上报页和救援信息页三个页面。
2. 打通信息创建、列表读取和实时推送。
3. 打通原信息编辑和实时替换。
4. 完成加载、成功、失败、空状态和断线重连。
5. 检查触控尺寸、文字可读性和页面简洁度。
6. P0 稳定后再评估紧急标记、处理状态、筛选和离线暂存。

## 15. 产品约束

任何新增功能进入设计或开发前,必须同时满足以下条件:

1. 能明显缩短救援信息的提交、查看或更新时间。
2. 不增加非必要页面。
3. 不增加用户必须理解的新手势。
4. 不让受灾人员首次上报超过 2 次核心操作。
5. 不让救援人员必须打开详情页才能读取核心信息。

不满足以上条件的功能不进入当前版本。
